# Spec System

> 核心发现：直接说"帮我做 X"效果很差。AI 需要结构化的上下文才能一次做对。
>
> 我们的方案：用 **grill-with-docs** skill 做结构化需求澄清，用 **Plan Mode** 做方案对比。没有使用模板文件，而是让 AI 主动反问来达成共识。

## 我们的方法：对话式规格化

和 OpenSpec 的"写 spec 文件"思路不同，我们的实践是**对话驱动**：

```
用户提模糊需求
  → /grill-with-docs（AI 一问一答，3-5 轮深挖）
    - 术语对齐："你说的'用户'是 Customer 还是 End User？"
    - 边界条件："失败后怎么恢复？哪些模块会受影响？"
    - 场景压测："两个 Agent 同时改一个文件怎么办？"
  → 确认完整需求后进入 Plan Mode
    - AI 提 2-3 个方案 + trade-off
    - 用户选方向
  → Claude Code 编写
```

**为什么不是文件模板？** 模板文件（proposal/design/tasks）的维护成本高，且我们只有一个人 + AI，不需要多人协作的文档流转。对话式澄清更轻量，确认后的共识自然记录在聊天历史中。

## 实测案例

**run-tests SKILL.md 优化**（2026-06-09）：

```
用户: "run-tests 太耗 token，功能不够完善"
  → grill-with-docs 反问 5 轮:
    Q1: 烧 token 的根因是 MCP snapshot 还是 SKILL.md 太长？
    Q2: 切换到 gstack browse 会不会失去灵活性？
    Q3: 风险有哪些？@e 引用失效、浏览器状态残留？
    Q4: 产物收集 6 项→2 项，Agent 代码输出是否已够？
    Q5: UI 常量提取到顶部，UI 改版时怎么办？
  → 每个问题给出建议答案，用户确认
  → Plan Mode 出 5 项修改计划
  → 实施：MCP→gstack 切换、产物精简、SKILL.md 216→103 行
  → /run-tests 验证
```

**效果**: SKILL.md 行数减少 52%，单次调用 token 消耗降低 ~70%。没有写过一份 spec 文件。

## AI 工作规范

以下是从实际协作中沉淀的规范，来自 CLAUDE.md + auto-memory：

| 阶段 | 规则 | 来源 |
|------|------|------|
| 动手前 | 先 Read/Grep/Glob 理解上下文，不盲写 | CLAUDE.md |
| 动手前 | 修改项目代码前先询问用户 | auto-memory |
| 动手前 | 复杂任务进入 Plan Mode 先出方案 | 工作流 |
| 编码中 | 优先编辑现有文件而非新建 | 实践 |
| 编码中 | 不处理不可能的错误场景，不做未来抽象 | CLAUDE.md |
| 编码后 | 编译/build 验证通过 | 实践 |
| 卡住时 | 3 轮无进展 → 换策略（写测试脚本 / 浏览器验证） | 实践 |

## 为什么对话式规格化有效

| 文件模板式 Spec | 我们的对话式 |
|-----------|---------|
| 写 spec 本身花时间 | AI 反问，用户只需做选择题 |
| spec 写完可能过时 | 聊天历史即文档，天然有时效性 |
| 模板字段容易流于形式（填满≠想清楚） | 每个问题推一个边界条件，倒逼想清楚 |
| 适合多人团队协作 | 适合 1 人 + AI 的快速迭代 |
