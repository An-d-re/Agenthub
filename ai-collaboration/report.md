## 二、AI Manager 能力模型

本项目的 AI 协作不是"AI 写代码、人看着"，而是**人作为 AI Manager，指挥 AI 完成复杂工程任务**。以下是我们验证过的 AI Manager 核心能力：

| 能力维度 | 具体表现 |
|----------|---------|
| **任务拆解** | 将模糊目标（"看看有没有 bug"）拆成可执行的 AI 指令（"派生独立子 Agent 探索代码库，输出带行号的 bug 清单"） |
| **工具路由** | 根据问题类型选择正确的 AI 工具：审查用 `/review`、查 bug 用 `/investigate`、全面测试用 `/qa` |
| **进度把控** | 给 AI 明确的交付边界（"实现这4项"、"先 commit 再 QA"、"测试脚本不提交"） |
| **质量验收** | AI 修完不是终点——要求 AI 自测、编译验证、浏览器实际跑、看不懂就要求解释 |
| **策略切换** | AI 卡住 3 轮无进展 → 换策略（写测试脚本、换 skill、直接调 API 验证） |
| **增量反馈** | 不一次说完所有要求，每人一轮给最关键的 1-2 条反馈，AI 修正后再给下一轮 |

### 2.1 阶段式协作流程

我们建立了 **"需求澄清 → AI 方案 → 人工审查 → AI 实现 → 人工验证"** 的五步循环：

```
用户提需求
  → AI 探索代码库、理解现状
  → AI 提 2-3 个方案（含 trade-off）
  → 用户选择方向
  → AI 实现 + 自测
  → 用户运行验证 → 进入下一个循环
```

**关键实践：AI 先探索再回答。** 每次收到需求，AI 会先 `Read`/`Grep`/`Glob` 相关文件理解上下文，再给出建议或写代码。我们从未要求 AI "盲写"代码。

### 2.2 文档驱动开发

项目维护了多份"AI 可读"的文档，让 AI 快速进入上下文：

- **`CLAUDE.md`** — 项目架构、命令、约定、当前进度的动态索引（AI 每次对话自动加载）
- **`改进.md`** — 架构审计报告（外部专家视角），驱动了 6 个 Phase 的架构升级
- **`issues.md`** — P0/P1/P2 问题追踪，AI 按优先级逐一修复
- **`前端要求.md`** — 设计规范，驱动了 Apple HIG 风格的 UI 重设计

**启示：为 AI 维护"活的"项目文档，比写死的 README 有用 10 倍。** CLAUDE.md 在每次功能完成后同步更新，确保 AI 始终知道项目最新状态。

### 2.3 计划模式

对于复杂任务（跨多文件、影响架构），我们使用 AI 的 Plan Mode：

```
用户说"按改进路线图改进多agent协作功能"
  → AI 进入计划模式
  → 写出 20 天实施计划（6 Phase，每个 Phase 的任务拆分、依赖、风险）
  → 用户批准 → AI 逐 Phase 实现
```

**启示：Plan Mode 消除了"AI 干了一半发现方向不对"的问题。** 计划是对话的锚点。

### 2.4 并发 Agent 探索

当需要大范围审计时，同时派出 2 个 Explore Agent 并行探索前后端，各自返回审计报告，人类做最终判断。这种方式在一次对话中发现了 14 个 bug。

## 三、关键 AI 辅助决策

### 3.1 架构升级：从 God Object 到 Phase Handler

**背景：** `orchestrator.py` 增长到 1206 行，用 `if phase == "clarify" elif phase == "comparison" ...` 做路由。

**AI 输入：** 用户提供了外部专家的架构审计（`改进.md`），AI 分析了 gstack 项目的设计模式。

**AI 方案：** Phase Handler 架构 — 每个阶段独立 Handler，registry 模式路由。gstack 的 "thin harness, fat skills" 设计哲学直接应用到了这里。

**结果：** 1206 行拆成 7 个文件共 ~900 行，每个 Handler 独立可测。新增阶段只需加一个文件 + 注册。

### 3.2 双层 Reviewer

**问题：** Reviewer 只靠 LLM 判断，token 消耗大，语法错误也要调 API。

**AI 方案：** Layer 1 静态规则（Python AST / JS 括号匹配 / JSON 解析 / 安全扫描），零 token 成本拦截基础问题。Layer 2 才用 LLM 审架构和逻辑。

**启示：AI 提出的"规则 + LLM 双层"模式，把"先排除确定性错误"的工程思维编码进了系统。**

### 3.3 深度思考可视化

**用户需求：** 想看到 Agent 的推理过程，像 DeepSeek 网页版那样。

**AI 探索：** 读 DeepSeek API 文档 → 发现 `reasoning_content` 字段 → 开启 `thinking: {type: "enabled"}` → 新增 `chat.stream.reasoning` 事件类型 → 前端折叠式面板。

**启示：AI 理解了"可视化推理链"这个抽象需求，找到了最底层 API 能力来实现它。**

### 3.4 14 个 Bug 的系统性发现

**方法：** 同时派出 2 个 Explore Agent，一个审后端一个审前端，要求输出精确文件路径 + 行号。

发现的 bug 涵盖：
- 逻辑错误（无限重试、文本确认不执行任务）
- 安全问题（路径穿越）
- 并发问题（信号量泄漏、DB 锁竞争）
- UX 问题（isThinking 卡死、token 覆盖、静默删除）
- 运维问题（沙箱未清理、event_bus 未退订）

**启示：AI 审计能发现人类 code review 容易漏掉的"交互层"bug（状态机卡死、事件覆盖）。**

### 3.5 独立 Agent 评审 + 批量短板修复

**背景：** 项目主体功能完成，需要对照竞赛要求（req.md）进行客观评估。

**方法：** 用户要求"派生一个独立的不相干的子 agent 来评判我们的项目并打分"。AI 派出 Explore Agent，提供 req.md 作为评审标准，要求输出 5 个维度的评分 + 具体优缺点。评审给出 89/100 分，指出 6 个短板（置顶交互缺失、测试覆盖极低、ErrorBoundary 未挂载、static_reviewer 未集成等）。

**后续行动：** 用户直接说"把短板的1、2、5、6实现了"，AI 并行探索 4 个相关文件 → 逐一实现 → 编译验证。其中 ErrorBoundary 发现已挂载（评审误判），立即跳过不浪费时间。

**启示：子 Agent 独立评审实现了"AI 检查 AI"的闭环。评审结果不是最终结论（1 项误判），需要人类交叉验证。**

### 3.6 4 轮调试：从表象到根因

**问题：** 置顶功能"点击了没反应、位置不变、群聊全冒出来了"。

**过程：**
- 第 1 轮：发现 `pinnedAt` vs `pinned_at` 字段名不匹配 → 统一 snake_case
- 第 2 轮：发现乐观更新 + 全量重拉冲突 → 改为 API-first 单条更新
- 第 3 轮：QA 浏览器测试发现真正的根因 —— `refreshSessions()` 从未在 mount 时调用，37 条历史会话根本不加载

**启示：每次修复后必须在浏览器中验证，不能只读代码推测。根因往往在上一轮修复的盲区里。**

## 四、Prompt 工程实践

### 4.1 最有效的 Prompt 模式

**"检查 → 报告 → 修复"链式 Prompt：**

```
"你进行头脑风暴，看看有没有不完善的地方，需要修改的错误，可以提升的地方"
→ AI 审计 14 个 bug
→ "按优先级修复吧"
→ AI 逐一修复并验证
```

**为什么有效：** 给了 AI 完整的探索自由度，然后给定清晰的执行指令。

### 4.2 遇到的黑洞 Prompt

以下 Prompt 模式容易让 AI 走向错误方向：

- **"帮我实现 XX 功能"**（无上下文）→ AI 会猜测实现方式，产生不必要的代码
- **"就这样吧"**（无明确验收）→ AI 停止思考，遗留边界情况

### 4.3 关键 Prompt 实例

| Prompt | 产出 |
|--------|------|
| "根据改进.md 和 gstack，制定改进路线图" | 6 Phase 架构升级计划 |
| "探索代码库，每个文件看一下，找出不一致" | 30+ CSS 变量不一致 |
| "同时审前后端，报告所有 bug，带行号" | 14 个 bug，按严重程度分类 |
| "尝试修复，修复不了告诉我 root cause" | 3 个 hypothesis 验证，1 个确认 |

## 五、AI 局限与应对

### 5.1 反复出现的模式

**"修 A 坏 B"模式：** 修复 `isThinking` 超时时，变量声明位置错误导致白屏。AI 马上定位并修复（"effectiveThinking 在 isThinking 之前引用了"），但问题本身源于前一步改动不够谨慎。

**应对：** 每次改动后要求 AI 运行 build 验证。2 次发现问题。

**"过度理论分析"模式：** 排查"第二条消息无响应"bug 时，AI 花了大量 token 在理论分析锁机制、事件循环调度上。最后通过写一个 WS 模拟测试脚本直接在真实环境复现，15 秒定位根因（DeepSeek API 延迟 + 锁排队）。

**应对：** 在 AI 分析超过 3 轮无结论时，人类介入要求"写个测试脚本直接测"。

### 5.2 AI 不适合做的事

- **主观设计判断**（"这个颜色好不好看"）— AI 能执行设计系统，但不能发明设计系统
- **一次性大重构** — AI 擅长增量改进，一次改太多文件容易引入 bug

## 七、核心经验总结

1. **CLAUDE.md 是 AI 协作的第一生产力。** 项目架构、当前进度、代码约定、已知问题都在里面，AI 每次对话自动加载。比任何 prompt 都有效。
2. **Plan Mode 消除方向性错误。** 复杂任务先计划再执行，比 AI 盲干效率高 3 倍。
3. **并发 Agent 做审计。** 前后端同时审，发现的 bug 比人工 code review 多。
4. **AI 不要猜 — 写测试脚本。** 与其分析 10 轮并发锁机制，不如写 30 行 WebSocket 模拟脚本。
5. **人为选择设计方向，AI 执行细节。** 配色、间距、圆角由人定调，AI 批量实施。
6. **增量改进 > 大重构。** 每个 commit 小且聚焦，减少 AI 出错面。
7. **字段命名一致性是静默 bug 的最大来源。** 前后端 JSON 契约必须 snake_case 统一，JavaScript 的 `undefined` 不报错但功能全坏。沉淀为 `rules/contract-safety.md`。
8. **QA 浏览器测试发现代码审查漏掉的 bug。** `useContacts` 孤儿 hook、`refreshSessions` 未调用 —— 这些代码审查很难发现，但浏览器一跑就暴露。
9. **AI 协作需要明确的 Git 纪律。** 不提交测试脚本、不 `git add -A`、每个 bug 一个 commit、破坏性操作必须确认。
10. **Skill 路由是高水平 AI 协作的标志。** 用户根据问题类型选择 `/review`、`/investigate`、`/qa`、`/debug`，而非泛泛的"修一下"。这是从 AI 工具使用者升级为 AI 指挥者的关键跃迁。
