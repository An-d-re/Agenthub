# AI 开发成功率提升案例

> 5 个具体的"用了这套体系 vs 没用的对比"案例，用数据证明 AI Manager 方法论的实际效果。

## 案例 1: 架构升级 —— God Object → Phase Handler

### 没有体系时（推测）
```
说："orchestrator.py 太长了，拆一下"
AI 做：可能拆成 2-3 个文件但不一定合理，新增 phase 还是要改主逻辑
Review：可能有遗漏的 if-else 分支
时间：估计 2-3 天 + 反复调试
```

### 用了体系后（实际）
```
1. 用户提供外部专家审计（改进.md）
2. AI 探索 gstack 项目的 Phase Handler 模式作为参考
3. Plan Mode 出 6 Phase 计划
4. 逐一实现，每 Phase 独立提交
5. Registry 模式保证扩展性
```

| 指标 | 数据 |
|------|------|
| 原始代码行数 | 1206 行 |
| 重构后 | 7 文件 ~900 行 |
| 新增 Phase 改动范围 | 1 个文件 + 1 行注册 |
| 回归 bug | 0 |
| 实际耗时 | 1 天 |

**关键方法**: Plan Mode + 外部参考（gstack）+ 增量提交

## 案例 2: 置顶功能 —— 从 4 轮调试到稳定交付

### 第 1-2 轮（无 Spec，无规则）
```
问题：字段名 camelCase/snake_case 不匹配
结果：JS 静默返回 undefined → pin 按钮无响应
耗时：~30 分钟排查
```

### 第 3 轮（有规则但未全覆盖）
```
问题：乐观更新 + 全量重拉在 store 中冲突
结果：会话列表闪烁、群聊突然全部出现
耗时：~20 分钟排查
```

### 第 4 轮（QA 浏览器测试发现真正根因）
```
问题：refreshSessions 未在 mount 时调用
结果：37 条历史会话完全不显示
耗时：~15 分钟（浏览器测试秒暴露）
```

### 沉淀产出
- 新增规则：`rules/contract-safety.md`（字段命名一致性 + 初始化副作用检查）
- 新增 Skill：`skills/index.md` S3（systematic-debug-loop）
- 新增 QA 经验：浏览器测试优先于代码审查

**核心价值**: 这一个功能踩的坑，变成了后续所有功能的保护网。

## 案例 3: 14 个 Bug 的系统性发现

### 方法
```
用户："你进行头脑风暴，看看有没有bug"
AI： 派生 2 个并行 Explore Agent
     Agent 1 → 审后端（27 个文件）
     Agent 2 → 审前端（22 个文件）
     输出：带文件路径 + 行号的 bug 清单
```

### 发现的 bug 分布
| 严重度 | 数量 | 类型 |
|--------|------|------|
| Critical | 4 | 无限重试、文本确认不执行、路径穿越、信号量泄漏 |
| High | 4 | isThinking 卡死、token 覆盖、静默删除、DB 锁竞争 |
| Medium | 6 | 沙箱未清理、event_bus 未退订、CSS 变量不一致等 |

### 人工审查介入
- 确认的 bug：13/14（93%）
- 误判：1 个（误报的并发问题）
- 人工修复的：2 个（涉及架构决策）
- AI 自修复的：12 个

**核心价值**: 2 个并行 Agent 在 10 分钟内完成了人工估计需要 2 天的全面审计。

## 案例 4: 会话列表不加载 —— 代码审查 vs 浏览器测试

### 问题
API 返回 38 条会话，前端只显示 1 条

### 代码审查路径（3 轮无效）
```
第 1 轮：检查 fetchSessions 逻辑 → 看起来没问题
第 2 轮：检查 LeftSidebar filter 逻辑 → 也没问题
第 3 轮：检查数据流 → 追踪不到断点在哪
耗时：~40 分钟，未定位
```

### 浏览器 QA 路径（1 轮定位）
```
1. 打开浏览器 → 看到只有 1 个群聊
2. curl API → 确认返回 38 条
3. 前端 JS 查 store → sessions.length = 1
4. Grep "useContacts" → 发现 hook 未被任何组件 import
5. Grep "refreshSessions" → 只在 handleAddMember/handleRemoveMember 中调用
6. 根因确认：没有在 mount 时调用
耗时：~10 分钟
```

**核心价值**: 浏览器测试在 10 分钟内定位了代码审查 40 分钟找不到的 bug。这是"代码审查 + 浏览器 QA"双轨验证的价值。

## 案例 5: 独立 Agent 评审 —— AI 检查 AI

### 场景
项目主体完成后，需要对照 req.md 竞赛要求进行客观评估

### 方法
```
用户："你派生一个独立的不相干的子 agent 来评判项目并打分"

AI： 派出全新 Explore Agent（无主对话上下文污染）
    提供 req.md 作为评审标准
    要求输出 5 维度评分 + 分项理由 + 短板清单
```

### 评审结果
| 维度 | 权重 | 得分 |
|------|------|------|
| AI 协作能力 | 30% | 28/30 |
| 功能完整度 | 25% | 21/25 |
| 生成效果质量 | 20% | 18/20 |
| 代码理解度 | 15% | 14/15 |
| 创新与产品感 | 10% | 8/10 |
| **总分** | | **89/100** |

### 评审指出的 6 项短板
1. 置顶交互缺失 → 已修复
2. 测试覆盖极低 → 从 0 增加到 33 用例
3. ErrorBoundary 未挂载 → 发现已挂载（评审误判）
4. static_reviewer 未集成 → 已集成到执行流
5. CodexAdapter 空桩 → 架构预留，暂不修复
6. P2 功能未完成 → 明确标注范围外

### 人工交叉验证
- 正确判断：5/6（83%）
- 误判：1/6（ErrorBoundary 实际已挂载）

**核心价值**: "AI 检查 AI"实现了独立于主 Agent 的质量闭环。评审结果不是最终结论（需要人工交叉验证），但比开发者的自我审查更客观。
