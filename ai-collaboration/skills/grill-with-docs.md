# grill-with-docs — 需求深挖与设计对齐

> **设计背景**: 直接对 AI 说"帮我做 X"是最常见的低效模式——AI 会猜测需求边界，猜得越多错得越多。Superpowers 和 OpenSpec 的理念都强调"先澄清再动手"。这个 skill 将需求澄清变成一个结构化的反问流程：逐层遍历设计树，每层给出建议答案等用户确认。
>
> **核心决策**: 不在 SKILL.md 中硬编码业务逻辑，而是定义"如何问"的元规则——挑战模糊术语、追问边界条件、用具体场景压测。这样同一套 skill 可以用于任何需求（UI 改版、架构升级、bug 修复），不限于特定领域。
>
> **所属层级**: OpenSpec 规格层（需求→可审查的规格）

---

## 触发

`/grill-with-docs` 或在对话中说"帮我分析一下需求""看看还有什么遗漏"。

适用于任何需要确认完整需求后才能动手的场景。与 Superpowers 的 Plan Mode 配合使用：先 grill 澄清需求 → 再 plan 出方案 → 然后 code 实现。

## 核心行为

逐层深挖设计树，每个分支逐个问题确认。**一次只问一个问题**，每个问题给出建议答案，等用户反馈后再继续。

优先级：代码库能回答的问题 → 直接探索代码库回答，不浪费用户时间。必须由用户决策的问题 → 才提问。

## 提问维度

### 1. 术语对齐

当用户使用模糊或过载的术语时（如"用户"到底是 Customer 还是 User？），立即指出并要求精确定义。如果项目有 CONTEXT.md 术语表，交叉校验。

### 2. 边界条件

- "什么场景下不需要这个功能？"
- "失败后怎么恢复？"
- "哪些模块会受影响？"

### 3. 场景压测

用具体的边缘场景逼迫精确化：
- "如果用户在支付过程中退出，订单状态应该是什么？"
- "两个 Agent 同时修改同一个文件怎么办？"

### 4. 交叉验证

当用户声称"代码是这样工作的"时，实际读代码验证。发现矛盾立即指出。

### 5. 文档同步

当术语或决策确认后，更新 CONTEXT.md（术语表）或 ADR（架构决策记录）。不批处理——每次确认立即记录。

## 使用方式

在我们的工作流中，grill-with-docs 是**每次新任务的第一步**：

```
用户提需求
  → /grill-with-docs（AI 反问 3-5 轮，确认完整需求）
  → 进入 Plan Mode（AI 出 2-3 个方案 + trade-off）
  → 用户选方向 → Claude Code 编写
  → /run-tests（浏览器自动化回归）
  → /debug-session（如有异常则诊断修复）
```

## 设计哲学

- **不猜需求**：AI 的默认倾向是尽快完成请求，这个 skill 刻意逆转这个倾向——先充分理解再动手
- **结构化追问**：不是随机提问，而是按术语→边界→场景→代码验证的顺序逐层深挖
- **人控方向**：AI 给建议但不替用户做决策，每个关键选择都等用户确认
- **即时沉淀**：确认的决策立即写入文档，不依赖聊天记录持久化
