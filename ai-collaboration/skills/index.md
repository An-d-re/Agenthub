# AI Manager Skills

> 人机协作中可复用的管理技能定义。这些不是 AI 的技能，而是**你作为 AI Manager 指挥 AI 的协作模式**。每个 skill 含触发条件、执行步骤、在本项目中的实际案例。

## S1. independent-review — 独立评审

**触发条件**: 需要客观评价项目完成度、代码质量、或方案优劣时。

**执行步骤**:
1. 提供评价标准（如 req.md 的评分维度）
2. 派生独立子 Agent（Explore agent），让它自主探索代码库
3. 要求输出评分 + 分项理由 + 未完成项 + 综合评价
4. 人类审查评审结果，对照自己的判断决定采纳哪些

**实测案例**: 用户让 AI "派生一个独立的不相干的子 agent 来评判我们的项目并打分"。AI 派出 Explore Agent 深度探索代码库，给出了 89/100 的评分，指出了 6 项短板（置顶交互缺失、测试覆盖极低、ErrorBoundary 未挂载、static_reviewer 未集成等），其中 4 项随后被修复。

**关键原则**: 子 Agent 不与主 Agent 共享上下文，保证评审独立性。

## S2. batch-parallel-fix — 批量并行修复

**触发条件**: 有多个独立 bug 需要修复，且它们不共享依赖。

**执行步骤**:
1. 列出所有待修复项
2. 并行探索所有相关文件（一次 `Read`/`Glob`/`Grep` 调用）
3. 按复杂度排序：简单 → 先做，复杂 → 后做
4. 每完成一项立即标记完成
5. 全部完成后运行编译/tests 验证

**实测案例**: 用户说"你把短板的1、2、5、6实现了"，AI 创建 4 个 task，并行读取 4 个相关文件，然后逐一实现。ErrorBoundary 发现已挂载（评审误判），立即标记完成不浪费时间。

**关键原则**: 先并行探索，再顺序执行。不重复探索已知信息。

## S3. systematic-debug-loop — 系统性调试循环

**触发条件**: 修复后 bug 仍然存在，用户反馈"还是有问题"。

**执行步骤**:
1. 不假设修复正确 — 从头追踪完整数据流（前端→API→后端→返回）
2. 用实际数据测试 API（curl 直接调后端）
3. 检查中间层转换（JSON 序列化、字段名映射、状态更新）
4. 写最小复现脚本（浏览器 JS / curl 脚本）
5. 找到根因后，用最简方式修复（最小 diff）

**实测案例**: 置顶功能经历 3 轮调试：
- 第1轮：发现 `pinnedAt`/`pinned_at` 字段名不匹配 → 统一为 snake_case
- 第2轮：发现 `togglePin` 乐观更新 + 全量重拉冲突 → 改为单条更新
- 第3轮：发现会话根本没加载（`refreshSessions` 未在 mount 调用）→ 这才是根因

**关键原则**: 不要相信上一次修复一定正确。追踪完整数据流而非局部代码。

## S4. qa-driven-fix — QA 驱动的原子修复

**触发条件**: 需要验证功能是否正常工作。

**执行步骤**:
1. 确保工作区干净（先 commit 或 stash）
2. 打开浏览器导航到目标页面（`/qa` 或直接 browse）
3. 截图 + 检查 console → 记录问题
4. 定位源码 → 最小修复 → atomic commit → 重启验证
5. 对比 before/after 截图
6. 如有 regression → `git revert HEAD`

**实测案例**: `/qa` 发现 `useContacts` hook 定义了但从未被任何组件调用，导致 37 条历史会话完全不显示。修复：`ChatPanel` mount 时调用 `refreshSessions()`。commit: `b1069e7`。

**关键原则**: 每个 bug 一个 commit，方便 revert。测试用浏览器实际验证，不只读代码。

## S5. incremental-fix-with-feedback — 增量修复 + 用户反馈

**触发条件**: 复杂功能需要多轮迭代才能正确。

**执行步骤**:
1. 实现最小可行版本
2. 启动服务让用户验证
3. 用户反馈 → 精确定位问题 → 修复 → 再次验证
4. 每轮修复记录：尝试了什么、为什么失败、正确做法是什么

**实测案例**: 置顶功能从"点了没反应"到"位置不变"到"群聊全冒出来了"到最终正常，经历了 4 轮迭代。每轮用户给出具体反馈，AI 缩小排查范围。

**关键原则**: 用户反馈是最高价值信号。不要防御性解释，直接查问题。

## S6. git-discipline — Git 操作纪律

**触发条件**: 每次修改代码后。

**执行步骤**:
1. 仅 stage 相关文件（`git add <specific-files>`，不用 `-A`）
2. Commit message 格式：`type(scope): description`（如 `fix(qa): ISSUE-001 — ...`）
3. 一个 commit 只做一件事
4. 不提交测试脚本到仓库（用户明确要求）
5. Commit 前确保编译通过

**实测案例**: 用户说"测试脚本不需要提交到仓库"，AI 停止提交测试脚本。后续用户要求清理工作区时，AI 先问用户如何处理（commit/stash/abort）而非自作主张。

**关键原则**: Git 操作由用户决策。destructive 操作（force push、reset hard）必须确认。

## S7. explore-before-build — 先探索再动手

**触发条件**: 收到任何需要修改代码的请求。

**执行步骤**:
1. 读 req.md / overview.md 等需求文档理解背景
2. `Read`/`Grep`/`Glob` 相关文件理解当前状态
3. 确认理解正确后，简述方案
4. 用户确认方向 → 开始写代码

**实测案例**: 用户第一次对话从"读 overview.md 和 req.md"开始，AI 探索了整个代码库后才更新 CLAUDE.md。修复 4 个短板时，AI 先并行读了 4 个相关文件才动手。

**关键原则**: 不要盲写代码。AI 先建立完整上下文再行动，比人类直接告诉 AI"改这个文件"效率高得多。
